# 附录C　AgenticOps 方法手册

正文里讲到"运行管控""控制面""模型网关"的地方，都只说了为什么要做。这份附录写给真正要动手搭系统的人，说明怎么做。不做技术工作的读者可以跳过。

## 从 DevOps 到 AgenticOps

软件进入大规模生产以后，写完代码不再是终点。DevOps 把开发、测试、发布和运行连成一条线，让系统可以频繁变化而不必每次推倒重来。机器学习进入生产后，代码之外又多了数据和模型，MLOps 管的是训练数据、实验、模型版本和漂移，程序没变，数据分布变了，模型也可能失效。

智能体又往前走了一步。模型会围绕目标选择步骤、读资料、调工具、用别人的身份和权限去改变现实。系统的行为由模型、提示、知识、记忆、工具、权限、运行环境和人的判断共同决定，其中任何一项变了，结果都可能跟着变。

| 方法 | 主要管什么 | 最关心的问题 | 单独使用时的缺口 |
|---|---|---|---|
| DevOps | 代码、服务、基础设施 | 能否稳定构建、发布和运行 | 判断不了概率输出和任务结果对不对 |
| MLOps | 数据、实验、模型、漂移 | 模型能否训练、验证和更新 | 通常不覆盖工具链、委托身份和外部后果 |
| AgenticOps | 任务、智能体、模型、上下文、工具、权限和结果 | 机器有没有在边界内做完对的事，能不能停下、复盘、改进 | 仍需要法律、组织责任和行业判断来约束 |

二〇二五年，开源模型社区 OpenCSG 提出了 AgenticOps 的说法，把智能体的生命周期分成提示、编码、构建、测试、发布、部署、运行和再训练八个环节。[^p4-agenticops-origin] 业界也常用 AgentOps，含义从可观测性到完整的生命周期管理都有，名称至今还没统一。[^p4-agentops-landscape] 本书用 AgenticOps 指一整套方法，它要让会行动的 AI 在整个生命周期里任务有边界，身份认得出，行动管得住，过程看得见，结果验得了，失败收拾得了，经验攒得下来。

## 三个循环和一个控制面

把这套方法画成一条从左到右的流水线，容易让人以为上线以后只要收数据、再训练、发下一版。真实的运行更像三个咬在一起的循环。

交付循环包括准入、设计、构建、评测和发布。它决定什么任务值得交给智能体，失败的边界怎样写进设计，模型、提示、知识、工具和权限怎样组成一个认得出的版本，拿到什么证据才能上线。

运行循环发生在每一项真实任务里：谁发起，智能体代表谁，这一步需要什么权限，外部动作有没有真的成功，什么时候必须停下来问人。

学习循环包括收集反馈、分析事故、做出变更、重新评测，必要时让智能体退役。真实的失败可以变成回归测试，人工的修改可以暴露规则的空白，投诉可以揭示评测没覆盖到的人群。

三个循环共用一个控制面，它保存几组稳定的对应关系：任务和责任人，智能体和身份，工具和权限，组件和版本，测试和发布门，运行轨迹和外部结果，成本和预算，事故和退出路径。控制面不必是一个平台，身份系统、工作流、模型网关、资产仓库、评测服务、运行遥测和审批制度组合起来就可以。要紧的是一项任务的信息能从立项一路连到结果和补救。

### 框架下面的六类方法

工程团队每天用的是更细的方法。二〇二五到二〇二六年间，智能体工程里逐渐形成了六类互相衔接的做法。[^p4-agent-engineering-methods-2026]

| 方法 | 改造什么 | 典型动作 | 容易被误解成 |
|---|---|---|---|
| 提示工程 | 单次推理的指令 | 写清角色、约束、示例和输出格式 | 管理了全部上下文 |
| 上下文工程 | 每一步模型实际看到的信息 | 按需检索、压缩历史、维护工作记忆 | 把资料全塞进窗口 |
| 工具与技能工程 | 智能体能调用的行动接口 | 缩小工具范围、校验参数、写清返回含义 | 接上 API 就算集成完了 |
| 运行装置工程（harness） | 模型外侧推动任务的整套环境 | 设计循环、计划、状态、检查点、恢复、批准和沙箱 | 买一个开发框架 |
| 评测驱动开发 | 能力和变化的验收方式 | 先定任务和评分规则，多次试验，检查轨迹和外部结果 | 只看最终回答或排行榜 |
| 轨迹驱动优化 | 已发生任务留下的过程证据 | 从失败轨迹里挑案例重放，比较改动 | 把所有日志拿去训练 |

检索增强、记忆、压缩属于上下文工程的具体机制；MCP 是连接工具的协议；多智能体是一种分工模式；沙箱、最小权限和人工批准是安全控制。它们都重要，单拿哪一个出来都撑不起整个框架。

### 运行装置（harness）

模型本身只会根据当前输入产生下一步输出。harness 在模型外侧维持"观察、判断、调用工具、拿到结果、继续或停止"这个循环，并决定这一轮给模型看什么、允许它碰哪些工具、状态写在哪里、什么时候压缩、什么时候检查、失败后从哪里恢复。

二〇二六年，OpenAI、Anthropic 和微软都公开了各自的 harness 工程做法，几家在模型上竞争最激烈的公司，在这件事上的结论却差不多：工程对象已经从"调好一个模型"扩大到"设计模型所在的工作环境"。[^p4-harness-engineering-2026] 同年八月，DeepSeek 以 MIT 协议开源了 DeepSeek Harness 的开发者预览版，从模型适配器、工具注册表到智能体循环本身都做成可替换的插件，官方说法是"模型加 Harness 等于 Agent"。发布方也提醒，这是早期预览版本，还有许多细节要打磨，后续会有不兼容的改动。[^p4-deepseek-harness-2026]

harness 本身也要有版本、要评测、要退役。旧 harness 为旧模型补上的种种限制，换了新模型以后可能变成累赘。

## 八类要一起登记的对象

传统模型平台主要登记模型、数据和实验。系统开始行动以后，只登记"用了哪个模型"，就像只登记谁进了办公楼，不登记他进了哪个房间、动了哪份文件。

| 对象 | 要回答的问题 |
|---|---|
| 目标 | 谁定义的任务，成功和禁止的条件是什么，目标变了旧任务要不要继续 |
| 主体 | 人、组织、智能体、外部服务各是谁，谁代表谁，责任能否沿委托链还原 |
| 上下文 | 数据从哪来，新不新、全不全、可不可信，敏感信息有没有超出必要范围 |
| 系统版本 | 实际跑的模型、提示、知识、记忆策略、工具说明和运行环境是什么 |
| 工具 | 谁提供，版本可不可信，参数和返回怎样校验，动作能不能撤回 |
| 权限与凭证 | 能访问什么、做什么、多久、能否再委托、怎样收回 |
| 任务状态 | 执行中、等输入、等批准、失败、取消还是完成，重试安不安全，预算还剩多少 |
| 外部结果 | 现实里哪些状态已经改变，是否真的完成，能否撤销、补偿、向受影响的人说明 |

这八项任何一项脱节，都会制造责任断点：日志记下了工具调用，却不知道用的谁的权限；知道模型版本，却不知道检索了哪份制度；任务标着"完成"，却没有外部订单号。

所以一个组织最先需要的是一本智能体登记册，至少写清：有哪些智能体，服务什么任务，谁负责，用了哪些高风险工具，碰哪些敏感数据，当前版本和评测状态，怎样暂停和退役。个人和部门都能随手建智能体以后，风险会来自大量没人负责、长期握着权限、从没重新评测过的"影子智能体"。

## 运行循环：看见过程，核对结果

传统监控回答服务在不在线、延迟多高、错误码多少。智能体即使所有接口都返回成功，也可能做错了任务，用错了资料，把正确的结果发给了错误的人。

一份可用的执行凭证至少要连起这些事实：任务由谁发起、目的是什么；用了哪个智能体、模型、提示、知识和工具版本；输入从哪来；拿到了什么权限；哪里发生过重试、降级或人工批准；改变了哪些外部状态；最终结果有没有被外部系统确认。执行凭证记录的是能核对的事实，模型的"内心独白"既可能含敏感内容，也未必说得清真实原因，不必当证据保存。OpenTelemetry 的生成式 AI 语义约定正在统一这类字段，它同时提醒，提示内容和工具参数可能含敏感数据，默认并不采集；能记录的东西不一定都该永久保存。[^p1-otel-genai]

运行循环要做到五件事：

- 看得见：任务、身份、来源、版本、工具和外部状态能关联起来。
- 管得住：数据、资金、时间、工具和委托层数按风险设限，高风险动作要过独立的规则或人工检查。
- 停得下：能取消任务、收回凭证、暂停单个工具，把系统降到只读或交给人工。
- 退得回：关键状态有快照，重复调用尽量不产生重复后果，版本能回退，已经造成的后果有补偿办法。
- 说得清：出现争议时，能根据当时的任务、依据和批准说明发生了什么，不靠模型事后编一段解释。

告警必须有负责人、响应时限和能执行的措施。发现工具调用量异常却没人能暂停，这样的日志等于事故直播。

## 学习循环：反馈怎样进入改进

运行越久，系统越懂真实工作，这是 AgenticOps 最吸引人的地方，可"收集、训练、再发布"不能变成自动飞轮。用户可能误点确认，历史结果可能含着歧视和错误，攻击内容可能故意混进记忆。

反馈进入学习之前，先回答：为什么收集，有没有权利用来改进；代表哪些人群和任务；质量怎样核验；人工修改是个人偏好、纠错还是制度要求；保留多久，谁能删除。

一次失败可以走不同的路：模型没理解任务，改提示、示例或换模型；检索到了旧制度，修知识库和时效机制；工具参数错了，加强校验；权限给宽了，改授权；任务目标本身含糊，重写任务说明；人总是否决某类动作，也许说明这件事不适合自动做。再训练只是其中一条路，往往还是最贵、最难解释的一条。

任何变更都要重新过发布门，旧版本通过的测试不能自动继承。最后一种学习是知道什么时候该停。微软二〇二六年的智能体生命周期实践把退役列为正式阶段，要求每个智能体有持续的责任人、监控计划和改进或退出路径。[^p4-agent-lifecycle-2026] 退役时要撤销身份和接口，处理剩余数据，保存必要证据，逐项解除下游依赖，把提示、流程、评测和事故经验带回来。

## 共享控制面怎样保持分权

部门自治也需要企业级的公共设施，好比火车共享轨道标准、信号系统和时刻表，却不必把每节车厢的货物倒进调度中心。

联邦式控制面可以提供七项公共能力：统一的身份和信任根，能力目录，协议和数据契约的登记，策略模板，模型和工具登记，任务路由，跨部门的状态和审计索引。它不该默认保存各部门完整的提示、检索片段、原始日志和长期凭证，也不能变成绕过本地策略、能直接执行所有工具的超级账户。

中央规则和本地规则冲突时，按"共同底线加本地收紧"处理：企业规定禁止事项、最低日志和身份要求，部门可以按专业风险再收紧，不能降低共同底线。

跨部门任务用一个共同任务编号串起一串执行凭证。每个部门做完自己那一步，签发一条最小记录：请求摘要、契约版本、执行身份、模型或规则版本、批准状态、产出物的哈希、时间、有效期和下一责任方。详细的提示、检索内容和敏感数据留在本地。中央追踪系统知道任务走到哪、哪一步失败、哪些产出物已经过期；获得授权的调查者可以沿任务编号向各部门调取更详细的证据。[^p9-otel-control] 法务意见因法规变化失效时，系统能找到所有引用了它、还在运行的任务；某个模型版本出了缺陷，可以圈出受影响的步骤，不必停掉全企业的智能体。

控制面自己也要能替换。能力目录、任务状态、策略和执行凭证如果只能存在某个平台的私有格式里，就是把锁定往上挪了一层。

## 能力网络和控制面的七类关系

一项真实任务可能同时用到本地小模型、云端大模型、搜索服务、知识库、传统接口、代码沙箱、浏览器、外部智能体和握有批准权的人。危险在于，局部权限通过连接拼出企业从未授予过的整体权力。员工只能看自己的客户，客服智能体只能创建退款申请，支付工具只能执行批准过的退款；如果三者的身份没有和任务绑在一起，智能体就可能借着员工的登录状态，绕开"申请、批准、支付"的分离。

控制面要长期维护这些关系：

1. 任务和能力：哪项任务用哪种模型、工具或人。
2. 数据和计算：原始材料留在哪，经过批准的哪些字段能出去。
3. 身份和行动：谁代表谁，为哪项任务，多长时间，对什么对象能做什么，用短期、可撤销的凭证表达。
4. 版本和评测：每次变化都经过评测和小范围试运行。
5. 运行和证据：完整调用链看得见，可以导出。
6. 反馈和资产：人工纠正、失败样本、申诉变成企业自己的评测题、规则和知识，不只回流给供应商。[^p6-data-work]
7. 事故和退出：能暂停、降级、回滚，保留证据，必要时整体迁走。

物理位置不是唯一的边界。分布式云能把云厂商管理的软硬件放进客户自己的机房，可信执行环境能在不完全信任基础设施运营方时保护正在计算的数据。[^p6-confidential-hybrid] 这些技术证明的是"观察到的软硬件状态符合某项信任策略"，证明不了代码逻辑正确、模型输出可靠。谁定义可信环境，谁拿着密钥，证明失败时停不停，供应商走了能不能迁移，这些仍要自己回答。

## 模型网关

早期的 AI 应用常常直接连一个模型，开发很快，依赖也在第一天就写进了系统。应用多了以后，各团队各自保管密钥、各自选模型、各自记日志，供应商一改接口，许多应用要一起改。

模型网关把"用哪个模型"的决定从应用代码里拿出来，交还给企业。应用把请求交给网关，网关识别调用者和任务类型，检查数据级别，选出允许的模型，执行限流和脱敏，记录版本、成本和延迟，再把结果交回应用。

以一名员工请 AI 总结一份客户合同为例。请求带着员工身份、部门和任务信息进入网关；网关核对他有没有权读这份合同，识别出其中有商业机密，排除不允许处理这类资料的外部模型；遮掉不必要的个人信息，发给批准过的模型；结果回来后记录版本、配置、输入资料的标识和耗时，检查输出有没有不该泄露的内容，最后才交给员工。

按难度在大小模型之间分配请求已有研究支持。一项实验在特定数据集上把大模型调用减少了最多约四成，总体质量没有下降；后续研究也发现，这类方法成败的关键在于对回答质量的估计准不准。[^p6-model-routing] 路由规则要拿企业自己的评测数据来校准。

网关只管得到经过它的调用，应用自身的权限和业务校验仍要保留。网关的路由规则、日志格式和接口也要清楚可导出，否则企业只是把对模型的依赖换成了对网关产品的依赖。

备用模型必须真的跑过。不同模型对提示格式、工具调用、上下文长度和安全策略的处理都不一样，主模型输出的结构，备用模型未必守得住。备用模型应当定期跑同一套真实评测，最好平时就承担一小部分低风险流量。它不必和主模型一样强，只要关键业务能降级继续：慢一点，人多参与一点，非核心功能暂时关掉。

## Token、积分和机器预算

平台开始用积分（Credits）计价以后，最常见的误会是把它当成高级一点的 Token。如果一百积分只是兑换固定数量的模型调用，它仍是一张充值卡。只有当积分能买到模型推理、智能体执行、行业数据、工具、人工复核和责任保障，并且交付结果可以核验时，它才接近一种服务结算单位。

可信的任务结算至少要满足四个条件：

- 兑换透明：一单位积分能买什么，各部分费用怎样构成，规则变化能追溯。
- 结果可验：谁来定义完成，用什么证据，失败、部分交付和争议怎样处理。
- 预算可执行：智能体只能在明确的额度、用途和时间内采购，超限就停，或重新授权。
- 账本可迁移：任务记录、费用明细和履约证据能导出，积分不能变成又一道退出壁垒。

二〇二五年发布的 Agent Payments Protocol（AP2，智能体支付协议）尝试用签名的购买授权、支付授权和收据，把人的意图、智能体生成的订单和最后的付款连起来。国际货币基金组织的一份工作人员说明把智能体支付分成意图与编排、控制与授权、结算三层，并把 AP2 放在中间一层：概率模型可以在上游找方案，授权最终要由确定的规则决定，结算按指令执行，不做改动。[^p6-agent-payments] 余额只告诉你还能花多少，授权凭证说明能替谁、在什么条件下花，履约证据说明买到了什么，责任规则说明失败由谁承担。这几样在身份、评测和争议解决成熟以前，"智能体之间自动交易"仍是一个有待检验的设想。

## 最低可行版本

这套方法不要求每个人都搭复杂平台。一个小团队可以从一张任务单、几个独立账号、一套真实测试和一次停止演练开始：

1. 给每个重要的智能体指定一个责任人。
2. 列出它会接触的数据、工具和外部影响。
3. 把高风险动作放到独立的确认点。
4. 运行中只保存足够复盘的版本和结果证据。
5. 用真实的失败攒一个小评测集。
6. 让备用路径平时承担少量任务。
7. 定期收回过期权限。
8. 实际演练一次停止、接管和导出。

规模大了，再逐步加上统一登记、自动发布门、动态授权、全链路遥测、事故响应和资产治理。管控的强度随数据敏感度、行动权、影响人数、不可逆程度和运行时长一起提高。

这套方法也会走偏。一种是做成只有大企业买得起的治理软件，登记、审批、遥测、审计层层叠加，小团队被挡在门外，反倒帮了集中化。另一种是做成审批文书，任务说明锁在抽屉里，发布门变成签字，停止开关从没演练过。判断一套 AgenticOps 是真是假，我只问一件事：上一次停止演练是什么时候，谁在几秒内按下了停止。
