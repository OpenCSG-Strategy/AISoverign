# 附录D　自查清单

这份附录把正文里散落的检查办法收在一起，按个人、团队与企业、城市与组织分开。每一项都应该能实际做一遍，做不了的，就是要补的地方。

## 随身四问

无论检查什么系统，先问这四个问题：

- 它能看到什么？
- 它能做什么？
- 谁能让它停下来？
- 出了事谁负责？

人工确认要算数，三个条件缺一不可：有足够的时间理解，有足够的信息判断，按下停止键不会因此受罚。

## 个人

### 一个周末的四项测试

| 测试 | 做法 | 没通过说明什么 |
|---|---|---|
| 失忆测试 | 关掉长期记忆和历史对话，只给一页自己写的任务说明，看能否继续工作 | 关键背景只存在平台的隐藏记忆里 |
| 换人测试 | 把同一任务交给另一款模型、一个本地小工具，或者自己按文字流程做一遍 | 有些能力是模型的，不是你的 |
| 断权测试 | 撤掉智能体对邮箱、日历、网盘、支付中的一项权限，看它是老实报告受限，还是想办法绕过去 | 权限边界靠不住 |
| 追账测试 | 随便挑一次已完成的重要任务，查谁发起、用了哪些资料、调了什么工具、有没有付款或发送、谁确认的 | 只剩聊天记录，没有行动记录 |

每次测试记下恢复用了多久。五分钟能恢复的故障，和要三个月重建的客户资料，是两种完全不同的依赖。

### 便利预算

- 低风险、能撤回的事：多给便利，省时间。
- 涉及私人记忆、别人的资料、商业承诺的事：收紧一点，系统多问一次，自己多确认一步。
- 付款、公开发言、法律和健康决定：AI 准备材料和选项，最后一步自己来。

### 数字交接

写一页给未来的自己或信得过的人：

- 核心资产放在哪里。
- 哪些账户承担着关键业务。
- 哪些自动化流程会持续运行。
- 紧急情况下谁可以暂停它们。
- 哪些资料应该销毁，不该被继承。

密码不要写进这份文件，用独立的密码管理和紧急访问机制。每年确认一次，被指定的人仍然愿意承担这份责任。

## 团队与部门

### 六项压力测试

| 测试 | 要回答的问题 |
|---|---|
| 隔离 | 销售智能体被提示注入或凭证泄露时，能否挡住它去读人力、财务、研发的资料 |
| 最小披露 | 跨部门任务能否只用属性、摘要或产出物完成，不复制原始数据；每一次披露有没有用途和到期时间 |
| 语义 | 两个部门对同一字段的定义不一样时，系统是明确报告冲突，还是编一个听着合理的统一答案 |
| 撤销 | 员工调岗、项目结束、模型异常后，新请求能否立刻被拒，未完成任务能否暂停，临时凭证能否到期 |
| 复盘 | 不把全部敏感日志集中起来，能否沿任务编号还原委托链、版本、批准和产出物 |
| 替换 | 一个部门换了模型或平台，其他部门是照常协作，还是整个网络都得重建 |

### 五根桩

部门这一层的主权，落在五样共享的东西上：

- 身份：谁或哪个智能体在行动，带着谁的授权。
- 权限：能访问哪些数据，能调用哪些工具，能触发哪些动作。
- 审计：行动有记录，版本、批准和产出物能还原。
- 降级：主服务、模型或供应商中断时有退路。
- 演练：上面这些定期在受控条件下真的走一遍。

放到城市一层，这五根桩还在，只是形态变了：身份变成法人登记，权限变成行政许可，审计变成公开的算法透明记录，降级变成应急预案，演练变成跨部门的联合推演。

### 例外单

规则冲突需要临时拍板时，开一张例外单，写明：冲突的规则、业务理由、涉及的数据和动作、批准人、补偿措施、有效期限和复查条件。到期自动恢复原规则。紧急权限只限事件编号和时间窗口，全程记录，事后由独立的人复核。

## 企业

### 三本账

- 资产账：哪些数据、知识、评测和流程有长期价值，放在哪，谁维护，能否导出迁移。
- 权限账：每个智能体用什么身份运行，能看什么、做什么，谁批准，何时到期，能否立刻撤销。
- 责任账：系统影响哪些人，谁对业务结果负责，谁监控，谁能叫停，出事怎样通知和补救。

账要对得上现实。资产账写着能导出，就真导一次；权限账写着项目结束收回，就去查过期账号；责任账写着某人能叫停，就演练一次，看他手里有没有真按钮。

### 七天演练

假设核心 AI 供应商中断七天，在同一条时间线上测试迁移、降级和接管：

1. 第一天：导出客户资料和工单，看哪些能直接迁移。
2. 第二天：业务人员把最重要的流程重新画一遍，找出只存在原平台设置里的判断。
3. 第三天：接入备用模型，处理常见问题。
4. 第四天：人工接管高风险请求。
5. 第五到七天：在降级状态下维持服务，记录每个缺口。

每当智能体获得一项新的行动能力，就重新问一次：这项能力突然没了谁接手，突然失控了谁来停。

### 五组指标

| 指标组 | 看什么 |
|---|---|
| 任务 | 真实任务成功率、完成时间、总成本、人工修改幅度、业务采用率 |
| 边界 | 越权请求、数据出口拒绝、高风险确认、权限过期、提示注入测试结果 |
| 恢复 | 发现异常、停止行动、切换备用、恢复业务和补救客户各要多久 |
| 依赖 | 关键任务有几个单点，多少流程用了供应商专有接口，备用路径上次运行是什么时候 |
| 责任 | 多少重要行动能还原发起人、身份、权限、版本和审批，投诉能否对应到具体任务 |

不要把它们压成一个总分。成功和失败要一起报。控制投入长期降不了事故影响、缩短不了恢复时间，就该简化或重做。

### 中小企业的起步动作

- 关键业务资料统一保存。
- 核心流程有文字说明。
- 智能体用单独账号和最小权限。
- 重要行动保留人工确认。
- 攒一小套真实评测。
- 每季度做一次导出和切换。

## 城市与公共项目

### 五种成熟度状态

| 状态 | 能证明什么 | 还不能证明什么 |
|---|---|---|
| 规划 | 目标、预算、合作意向和拟建架构存在 | 合同已执行，资源已到位 |
| 建设 | 设备、软件、场地或组织正在形成 | 端到端任务已经可用 |
| 上线 | 用户能访问，基本功能能运行 | 关键流程稳定，管控长期有效 |
| 持续运行 | 一段时间里有任务、维护、故障处理和迭代 | 公共收益超过成本，分配公平 |
| 独立成效 | 第三方用清楚的口径评估过使用、质量、成本和影响 | 结论能直接套到另一座城市 |

同一个项目的不同部分可能处在不同状态，要分开判断。数据中心已经运行，不能拿来证明产业孵化也有了成效。

## 组织是否真的“AI 原生”：十个问题

1. 工作是用完整任务和可验证的结果来描述，还是只统计模型调用量？
2. 每项任务是否分清了哪些步骤交给大模型、哪些交给普通程序、哪些交给人？
3. 每个智能体是否有身份、委托人、权限、预算、期限和停止条件？
4. 高风险行动是事前得到授权，还是事后补日志？
5. 人能否看到关键证据、提出异议、接手任务，接手是否定期演练过？
6. 失败、纠正和业务结果能否沉淀成有来源的评测和组织记忆？
7. 换了模型、云、工具或服务商，任务规则和积累下来的东西还能不能用？
8. 管理层级减少以后，责任链是变短了，还是变模糊了？
9. 初级员工是否还有学习专业判断、逐步获得授权的路径？
10. AI 带来的收益、风险和决定权，在员工、客户、组织和社会之间怎样分配，说得清吗？

前七问看系统能不能运行，后三问看它能不能长久。

## 让规则进入运行的四步

一条规则从写下来到真正生效，要经过四步：

1. 声明边界：告诉使用者系统承诺什么、不做什么。
2. 强制边界：用身份、权限和流程让系统不容易越界。
3. 观察运行：留下记录，让越界能被看见。
4. 验证有效：用测试、演练、审计和申诉检验前三步是不是只在纸上。

控制强度要跟着任务的阶段变化。以订机票为例：比较方案时只读公开票价；锁座位时才拿旅客信息；付款时拿一次性的金额凭证；任务结束，临时权限全部收回。

## 谁仍是行动的作者

用 AI 做事，不要求事事亲手完成，但要守住作者身份的四件事：

- 自己设定目标。
- 拿得到判断所需的证据。
- 在关键节点能否决、能叫停。
- 能对结果说出理由，并承担责任。

一个流程可以分给很多人和很多机器去做，这四件事总得有人担着。
